# Ason Agent 优化计划 —— 让 7B 小模型真正能干活

> 基于 `docs/ollama-7b-comparison.md` 的对比分析，本计划列出可落地的优化方向。
> 每项都标注：**优先级**（P0/P1/P2）、**预期收益**、**改动范围**、**风险**。
>
> 总体思路：7B 小模型的根本问题是**推理弱 + 上下文短 + 易跑偏**。
> 优化策略围绕三条主线：
> 1. **降低模型负担**——用模板/示例/约束把"自由发挥"空间压到最小
> 2. **提高单步成功率**——让每一步都有"标准答案"可抄
> 3. **强化外部闭环**——把判断权进一步从模型剥离到确定性代码

---

## P0 优先级（投入小、收益大、风险低，建议先做）

### 1. 引入 Few-Shot 示例库（Tool Calling 模板）

**问题**：当前 systemPrompt（agent.js:130-143）只告诉模型"输出 JSON 调用工具"，但没有给出**正确示例**。7B 小模型对"看例子"的依赖远大于"读规则"。

**方案**：
- 在 system prompt 中为每个高频工具（read_file / list_dir / bash / apply_diff / write_file）附 1 个标准调用示例
- 示例放在工具列表之后，用 `### 示例` 分隔
- 控制总长度在 800 token 以内（避免挤占上下文）

**预期收益**：JSON 解析成功率显著提升，`JSON_RETRY` 触发次数下降，单轮收敛步数减少。

**改动范围**：`src/core/agent.js` 的 `systemPrompt()` 函数；新增 `src/core/prompts/examples.js` 集中管理示例。

**风险**：示例过长会挤占 16K 上下文，需精简。

---

### 2. 任务模板（Task Templates）—— 把高频任务固化为"配方"

**问题**：7B 自己规划多步任务容易跑偏、重复、漏步。但实际使用中，很多任务是**重复模式**（如"修 bug"、"加函数"、"重构命名"）。

**方案**：新增 `templates/` 目录，预定义常见任务的**步骤骨架**（不是脚本，是 prompt 引导）：

```
templates/
  fix-bug.md          # 修 bug：读相关文件 → 定位 → 改 → 跑测试
  add-function.md     # 加函数：找类似函数 → 模仿风格 → 实现 → 测试
  refactor-rename.md  # 重命名：grep 引用 → 批量改 → 跑测试
  explain-code.md     # 解释代码：读文件 → 给出结构化解释
```

每个模板包含：
- 任务识别关键词（前端匹配用户输入）
- 推荐工具调用顺序（作为 system 提示注入）
- 每步的"检查点"（提示模型该步该产出什么）

**触发方式**：
- 自动：用户输入命中模板关键词时，前端提示"检测到 X 任务，是否使用模板？"
- 手动：`/template fix-bug` 命令显式调用
- 模板不强制流程，只作为"建议路径"注入 system prompt

**预期收益**：把"模型自由规划"降级为"模型按图索骥"，大幅减少跑偏和步数浪费。

**改动范围**：新增 `src/templates/` 目录 + `src/core/template-loader.js`；`agent.js` 在 systemPrompt 拼接时注入模板内容；前端加模板选择 UI。

**风险**：模板过多反而增加模型选择负担，建议初版只做 4-5 个最高频模板。

---

### 3. 工具调用前的"预检查"（Pre-flight Check）

**问题**：7B 经常调用不存在的文件、传错参数类型（如把字符串传给需要数字的参数）。这些错误要等工具执行才暴露，浪费一步。

**方案**：在 `runTool` 之前加一层轻量预检：
- 文件类工具（read_file/write_file/apply_diff）：先检查文件是否存在，不存在直接返回提示，不调模型
- 参数类型校验：根据工具 schema 校验 params 类型，类型错误直接返回"参数 X 应为 Y 类型"
- 路径预归一化：在 safeResolve 之前先做一次"路径是否看起来合理"的启发式检查

**实现位置**：`src/core/agent.js` 的 `runTool` 调用处，包一层 `precheck(action, params)`。

**预期收益**：减少无效工具调用步数，把 MAX_STEPS 留给真正需要的步骤。

**改动范围**：新增 `src/core/precheck.js`；`agent.js` 调用处加一层。

**风险**：预检逻辑过严会误拦合法调用，需保留"跳过预检"开关。

---

### 4. 强化 System Prompt 的"行为约束"

**问题**：当前 systemPrompt 偏"描述性"（"只有需要时才调工具"），7B 对这种软约束遵守度低。

**方案**：改为"清单式硬约束"，用 `必须`/`禁止` 开头：

```
【行为规则】
1. 禁止在未读文件前就修改文件。
2. 禁止连续调用同一个工具超过 2 次（除非用户明确要求）。
3. 必须先 read_file 再 apply_diff，禁止凭记忆改文件。
4. 普通问答禁止调用任何工具，直接用 markdown 回答。
5. 调用工具后必须等待结果，禁止在同一轮里连续调多个工具。
```

**预期收益**：硬约束比软建议对 7B 更有效，重复调用、凭空改文件等行为减少。

**改动范围**：`agent.js` 的 `systemPrompt()` 重写约束部分。

**风险**：约束过多会让模型困惑，控制在 5-7 条以内。

## P1 优先级（投入中等、收益大，建议 P0 稳定后做）

### 5. 工具结果摘要化（Tool Result Summarization）

**问题**：当前 `TOOL_RESULT_MAX=6000` 字符直接回传模型。一次 `read_file` 大文件或 `bash` 长输出，可能吃掉 1/3 上下文。7B 在长输出里找关键信息能力弱。

**方案**：
- `read_file`：默认只返回前 100 行 + 后 20 行，中间用 `... (省略 N 行)` 替代；模型可调 `read_file(path, start, end)` 读指定区间
- `bash`：输出超过 50 行时，只保留前 10 行 + 后 10 行 + 包含 `error/Error/失败/异常` 的行
- `grep/semantic_grep`：默认 max=20，超出时提示"还有 N 条，可用 max=50 查看"
- 给每条工具结果加一行**机器生成的摘要**（如"文件共 345 行，含 3 个函数定义"），帮助 7B 快速定位

**预期收益**：上下文利用率提升，单轮能处理更大的文件/更长的输出。

**改动范围**：各工具的 `run()` 函数；可抽公共 `src/tools/utils.js` 的 `summarizeOutput()`。

**风险**：摘要可能漏掉模型需要的关键信息，需保留"查看完整输出"的逃生口。

---

### 6. 上下文注入"工作记忆"（Working Memory）

**问题**：7B 容易在多步任务中"忘记"前面读了什么文件、改了什么。当前靠消息历史，但历史会被截断/压缩。

**方案**：每轮 agent 循环开始时，在 messages 前注入一条**动态工作记忆** system 消息：

```
【当前工作状态】
- 已读文件：src/agent.js, src/config.js
- 已改文件：src/utils.js（修改了 safeResolve 函数）
- 已知问题：测试失败，报错 "Cannot find module './precheck'"
- 当前目标：修复模块导入错误
- 未完成步骤：还需要验证修复是否生效
```

这条消息由 agent 循环维护，每步更新，**永不截断**（优先级仅次于工具列表 system）。

**预期收益**：7B 在长任务中"知道自己干了什么"，减少重复读文件、重复改同一处的问题。

**改动范围**：`agent.js` 新增 `workingMemory` 对象 + 注入逻辑；压缩逻辑要识别并保留这条消息。

**风险**：工作记忆本身也占上下文，需控制条目数（建议上限 10 条）。

---

### 7. Plan Mode 输出结构化（Structured Plan）

**问题**：当前 Plan Mode 让模型自由输出"可确认的执行计划"，但 7B 输出的计划常常模糊、不可执行、与后续步骤脱节。

**方案**：强制 Plan Mode 输出固定 JSON 结构：

```json
{
  "goal": "用户目标的简短描述",
  "steps": [
    {"action": "read_file", "reason": "需要先了解现有实现", "target": "src/x.js"},
    {"action": "apply_diff", "reason": "修改函数签名", "target": "src/x.js"},
    {"action": "run_tests", "reason": "验证修改正确"}
  ],
  "risks": ["可能影响调用方", "需要同步更新测试"]
}
```

前端解析后渲染为可勾选的步骤列表，用户确认后逐步执行（每步可跳过/修改）。

**预期收益**：计划从"自由文本"变"可执行清单"，用户可干预，执行更可控。

**改动范围**：`agent.js` Plan Mode 分支；前端渲染；可能需要新增 `/api/confirm-plan` 接口。

**风险**：7B 可能输出不合规 JSON，需复用现有 `parseToolCall` 容错逻辑。

---

### 8. 模型路由（Model Routing）—— 任务分级匹配模型

**问题**：当前所有任务都用同一个模型（默认 `deepseek-r1:8b`）。但有些任务（如压缩摘要、生成 embedding 描述）对推理要求低，可用更小更快的模型。

**方案**：配置多模型路由：

```js
// config.js
const MODEL_ROUTING = {
  default: process.env.MODEL || 'deepseek-r1:8b',        // 主对话+工具调用
  compact: process.env.COMPACT_MODEL || 'qwen2.5:3b',    // 上下文压缩摘要
  embed: process.env.EMBED_MODEL || 'nomic-embed-text',  // embedding（已是）
  // 可选：简单问答用 1.5b 模型，省显存
  simple: process.env.SIMPLE_MODEL || 'qwen2.5:1.5b',
};
```

`compactMessages` 用 `compact` 模型；简单问候/解释用 `simple` 模型；复杂任务才用 `default`。

**预期收益**：本地显存有限时，小模型干小活，大模型干大活，整体吞吐提升。

**改动范围**：`config.js`；`compact.js` 改用 `MODEL_ROUTING.compact`；`agent.js` 可选根据任务复杂度选模型。

**风险**：多模型切换增加复杂度，初版可只做 compact 路由。

## P2 优先级（投入大或收益不确定，建议视情况做）

### 9. ReAct 范式改为 Plan-and-Execute

**问题**：当前 ReAct（推理-行动-观察）循环里，每一步都要模型重新推理"下一步干什么"。7B 在长链里容易丢失全局目标。

**方案**：新增 Plan-and-Execute 模式（与现有 ReAct 并存，可切换）：
1. **Planner 阶段**：模型一次性输出完整计划（步骤列表）
2. **Executor 阶段**：逐步执行，每步只把"当前步骤 + 上一步结果"喂给模型，不喂整个计划
3. **Replanner 阶段**：每 N 步或出错时，重新规划剩余步骤

**预期收益**：减少每步的全局推理负担，适合 7B 的短上下文特点。

**改动范围**：新增 `src/core/plan-execute.js`；前端加模式切换。

**风险**：改动大，需充分测试；Planner 输出质量直接决定成败。

---

### 10. 工具调用结果缓存（Tool Result Cache）

**问题**：7B 容易重复调用同一工具（如多次 `read_file` 同一文件）。当前有重复检测，但检测到后只是警告，还是会消耗一步。

**方案**：对只读工具（read_file/list_dir/grep/git_status 等）的结果做缓存：
- 同一轮 agent 循环内，相同 (action, params) 直接返回缓存结果，不重新执行
- 文件被 write_file/apply_diff 修改后，自动失效该文件的 read_file 缓存
- 缓存只在单轮循环内有效，新一轮对话清空

**预期收益**：减少无效步数，加快循环收敛。

**改动范围**：`agent.js` 加缓存层；写工具触发失效。

**风险**：缓存失效逻辑出错会导致模型基于旧内容修改，需谨慎。

---

### 11. 微调小模型（Fine-tuning）—— 终极方案

**问题**：通用 7B 模型对"Agent 工具调用"这一任务分布外（OOD），再多的 prompt 工程也有上限。

**方案**：收集本项目实际运行的（用户输入 → 正确工具调用）对，微调一个专用 7B：
- 数据来源：项目运行日志（需用户授权）+ 人工构造的高质量样本
- 微调方式：LoRA（低_rank 适配，显存友好）
- 目标：让模型"原生"理解 `{action, params}` 格式和工具语义，不再依赖 prompt 注入

**预期收益**：从根本上提升 7B 的 Agent 能力，减少工程兜底的负担。

**改动范围**：新增 `finetune/` 目录（数据收集脚本 + 训练脚本 + 评估脚本）；独立于主项目。

**风险**：投入大；需要持续收集数据；微调后模型可能过拟合本项目工具集。

## 实施建议

### 阶段一（1-2 周）：P0 全部落地
- Few-Shot 示例库
- 任务模板（先做 fix-bug / add-function 两个）
- 工具预检查
- System Prompt 硬约束重写

**验收标准**：用一组标准测试任务（如"读取 src/config.js 并解释"、"修一个简单 bug"）对比优化前后的步数、成功率、JSON 解析失败率。

### 阶段二（2-3 周）：P1 选择性落地
- 工具结果摘要化（优先做，收益明确）
- 工作记忆注入
- Plan Mode 结构化
- 模型路由（先只做 compact 路由）

### 阶段三（视情况）：P2 探索
- Plan-and-Execute 模式可作为研究课题
- 工具结果缓存作为体验优化
- 微调作为长期方向

| `json_parse_failures` | JSON 解析失败次数 / 总调用次数 | < 5% |

## 总结

7B 小模型"能干活"的关键不是让模型变强，而是**让模型不需要强**：

- **模板 + 示例**：让模型抄答案而非自己想
- **预检 + 硬约束**：让模型少犯错
- **摘要 + 工作记忆**：让模型在短上下文里不迷失
- **结构化计划 + 缓存**：让模型按图索骥而非自由发挥

把"智能"从模型层下沉到工程层，7B 也能稳定完成 80% 的日常编程任务。
