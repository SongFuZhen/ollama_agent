# ollama_agent 关键信息摘要

> 由多轮分析对话（《推测方案》《真实 README 分析》《优化建议书》《军工内网可行性》）提炼而成。纯文字与图示，无代码。

---

## 一、一句话定位

ollama_agent 是一个基于 Ollama 本地小模型（7B 级）的**内网零依赖 AI 编程助手**：数据不出内网、零 API 费用、复制即跑。

核心价值：数据不出内网 · 零 API 费用 · 完全可控。
核心瓶颈：7B 模型的推理能力、上下文长度、工具调用准确性有明显天花板。

---

## 二、核心设计哲学

    弱模型  +  强约束  +  真数据  =  不瞎编

这一等式贯穿整个项目，是对 7B 小模型能力缺陷的工程化应对。

    问题              解法                 实现手段
    ────────────      ────────────         ────────────────────────────
    模型易编造代码    真数据优先            Agent 主循环强制 tool-first
    模型不知何时停    强约束                单目录沙箱 + 写操作确认
    长对话丢上下文    上下文压缩            compact 自动摘要
    跨会话无记忆      三级记忆召回          L1 最近 → L2 语义 → L3 关联
    改完代码不可控    验证闭环              改完自动跑 run_tests / run_lint
    怕模型乱改        规划模式              /plan 只读调研 → 出计划 → 确认执行

## 三、它能做什么 / 不能做什么（7B 能力边界）

能做（靠谱，⭐⭐⭐ 以上）：单文件/模板代码生成、行级补全、代码解释、简单 Bug 修复、正则/SQL 生成、文件读写搜索、单测生成、格式化与重命名。

吃力（玻璃顶，⭐⭐ 以下）：跨多文件架构设计、10+ 文件重构、精确工具调用（易幻觉）、超 4K token 长上下文推理、多步复杂调试。

    7B 模型 ≈ 一个“聪明但缺乏经验的实习生”

      你不会对实习生说：
        “去，把这个项目优化一下”        ← 模型会乱来、胡说八道

      你会对实习生说：
        “按这个清单，一步一步做”          ← 模板约束下，模型够用了

    本质：把模型从“理解 + 推理 + 执行”降级为“按模板填空”。
    7B 做不好前者，但完全能胜任后者。

## 四、技术架构与四大亮点

    用户请求 → Web/CLI 前端 → Node 后端(Agent 框架) → Ollama API → 本地 7B 模型
                                        │
                                        └─ 工具调用层：文件读写 / 命令执行 / 代码搜索

亮点一 · 零依赖架构
    纯 Node 内置模块 + sql.js(WASM)，无 node_modules，npm install 完全跳过。
    U 盘直拷到内网机器即跑 —— 断网环境下是决定性优势。

亮点二 · 三级记忆系统
    L1 最近对话（短期工作记忆）→ L2 语义召回（向量相似搜索）→ L3 跨会话关联。
    多数简单 Agent 只做 L1，本项目做到了 L2/L3。

亮点三 · 三套命令优先级（确定性逃生舱）
    ! 直接执行 shell  >  @ 强制调工具  >  /plan 只读规划  >  自然语言完整循环
    小模型不靠谱时，用户可绕过模型直接驱动工具，保证确定性。

亮点四 · 写操作安全设计
    write_file / edit_file / apply_diff / bash / run_tests / run_lint 全部需用户确认 ✓
    读操作无感通过。这是对 7B “幻觉”的工程化防御。

## 八、军工内网可行性

可行性评分：⭐⭐⭐☆☆（3/5）

    能跑起来？      能，技术上完全可行
    能用起来？      勉强，体验远不如预期
    能产生价值？    有限，需要非常精准的定位
    值不值得投入？  取决于替代方案是否存在

直白结论：最大问题不是“能不能做”，而是“做了之后用户真的会用吗”。
最大坑：依赖审查 —— 虽零 npm 依赖，但仍有 express / ollama-js / better-sqlite3 等
一二十个需逐包过安全审查的组件，军工审查要逐一过关。

## 九、终极定位：模板化 Agent 工作流引擎（最该走的方向）

直觉正确 —— 7B 不该做“自由对话 Agent”，而该做“模板化工作流 Agent”。

    无模板（自由 Agent）              有模板（工作流 Agent）
    用户: “帮我优化性能”             用户: “执行性能分析模板”
         ↓                                ↓
    模型: ??? 该做什么？            模板: Step1 运行基准测试
         ↓                                ↓
    模型: 可能胡说八道              模板: Step2 读取结果
         ↓                                ↓
    用户: 不对…重来                 模板: Step3 按规则分析
         ↓                                ↓
    反复 5 轮，放弃                  模板: Step4 生成报告
    耗时 15 分 / 质量不确定          耗时 3 分 / 质量可预期

三层飞轮（核心模型）：

    ① 模板库沉淀      通用场景模板（代码审查 / Bug 定位 / 重构…）
          ↓
    ② 模板质量优化    打磨 Prompt 与步骤，让 7B 稳定产出
          ↓
    ③ 用户自定义模板  yaml 声明式，非代码，业务方自己写
          ↓
    飞轮：更多模板 → 更多场景 → 更多反馈 → 更好模板

最终判断：

    技术可行性   ★★★★★   完全可以做
    市场空白     ★★★★★   “小模型 + 模板化 Agent” 几乎没人做好
    差异化优势   ★★★★     现有方案都针对强模型，你针对小模型
    落地难度     ★★★      工作流引擎不复杂，模板质量与工具集成是核心
    用户价值     ★★★★     比自由对话可靠，比手工作业快

从“一个会写代码的聊天机器人” → “一套可编排的开发效率工具”。
一句话：能做，该做，而且可能是唯一能做成的路。
